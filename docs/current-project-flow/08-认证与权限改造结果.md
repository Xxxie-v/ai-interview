# 第二阶段：认证与权限改造结果

这一阶段只处理统一登录、账号状态、角色权限和数据归属保护，没有提前开发岗位、
面试任务、视频上传等后续模块。

## 已完成能力

### 1. 统一用户与登录身份

- `UserEntity` 增加昵称、头像和 `ACTIVE / DISABLED / LOCKED` 状态。
- 新增 `UserIdentityEntity`，手机号、微信和 QQ 身份都归属到统一系统用户。
- `(identityType, identifier)` 有数据库唯一约束。
- 微信优先使用 `unionId` 查找身份。
- 第三方 access token 使用 AES-GCM 加密后再保存。

核心文件：

- `modules/auth/model/UserEntity.java`
- `modules/auth/model/UserIdentityEntity.java`
- `modules/auth/service/IdentityTokenCipher.java`
- `modules/auth/service/OAuthIdentityPersistenceService.java`

### 2. 手机验证码登录

流程如下：

```text
POST /api/auth/sms/send
  -> 校验手机号和 IP 频率
  -> 后端生成随机验证码
  -> SmsService 发送
  -> Redis 保存验证码和有效期

POST /api/auth/sms/login
  -> 校验验证码和失败次数
  -> 验证成功后立即删除验证码
  -> 查找或创建 INTERVIEWEE 用户
  -> 签发 access token 和 refresh token
```

生产环境不会返回验证码，也不会在日志中打印完整手机号或验证码。本地使用
`APP_SMS_PROVIDER=noop` 且显式设置 `APP_SMS_EXPOSE_CODE=true` 时，接口响应才会携带
调试验证码。

### 3. 微信与 QQ OAuth2

实现统一的 `ThirdPartyOAuthClient`，以及 `WechatOAuthClient`、`QqOAuthClient`。
浏览器只能提交授权平台返回的 `code`；用户标识由后端向微信或 QQ 获取，不能由前端
伪造。随机 `state` 保存在 Redis 中，并且验证后立即删除。

接口：

```text
GET  /api/auth/oauth2/{provider}/authorize
GET  /api/auth/oauth2/{provider}/callback
POST /api/auth/oauth2/{provider}/bind
```

`provider` 只允许 `wechat` 和 `qq`。

### 4. 角色、账号状态和令牌

- 固定角色收敛为 `ADMIN` 与 `INTERVIEWEE`。
- 普通注册只能得到 `INTERVIEWEE`，不能通过“第一个注册用户”等方式获得管理员权限。
- 启动时会把旧的 `HR` 角色归并到 `ADMIN`，把 `CANDIDATE / USER` 归并到
  `INTERVIEWEE`。
- 每次携带 JWT 请求时都会重新读取用户状态，因此账号被禁用或锁定后，已签发的
  access token 立即不可用。
- 禁用或锁定用户时会同步撤销其全部 refresh token。
- JWT 中只有用户 ID、用户名、角色、权限和有效期等鉴权字段，不包含手机号、邮箱、
  密码或第三方 token。

管理员账号接口：

```text
GET   /api/admin/users?page=0&size=20
PATCH /api/admin/users/{userId}/status
```

状态修改请求示例：

```json
{
  "status": "DISABLED"
}
```

管理员不能禁用或锁定自己的账号，避免误操作导致管理入口全部丢失。

### 5. 防止越权读取

新增三个统一权限组件：

- `ResumePermissionService`
- `InterviewPermissionService`
- `VideoPermissionService`

简历、文字面试和语音面试接口增加方法级 `@PreAuthorize` 与资源所有者判断。只修改
URL 中的 `resumeId` 或 `sessionId`，不能读取或操作其他用户的数据。

浏览器 WebSocket 不能像普通请求一样可靠地附带 Authorization 请求头，因此语音面试
连接使用短期 access token 查询参数。`VoiceInterviewHandshakeInterceptor` 在握手阶段同时
验证 JWT、用户当前状态和会话归属；`/ws/**` 虽在 HTTP 路由层允许握手进入，但未通过
拦截器认证的连接仍会被拒绝。

## 数据库变更方式

本项目现有约定是由 JPA Entity 注解驱动表结构，开发环境使用 `ddl-auto=update`，没有
Flyway 或 Liquibase。因此本阶段没有新增迁移脚本，新增或变化的表结构包括：

- `auth_user`：增加 `nickname`、`avatar_url`、`status`，密码哈希允许为空。
- `auth_user_identity`：新增第三方/手机号身份表及唯一索引。
- `auth_role`、`auth_user_role`：启动时完成旧角色数据归并。

生产环境 `ddl-auto=false` 时，应由运维根据上述 Entity 生成并审核 DDL 后执行，不能直接
依赖应用自动改表。

## 关键配置

至少需要检查 `.env` 中的以下配置：

```dotenv
APP_AUTH_JWT_SECRET=至少32位随机字符串
APP_AUTH_IDENTITY_ENCRYPTION_KEY=另一组至少32位随机字符串
APP_SMS_PROVIDER=noop
APP_SMS_EXPOSE_CODE=true

APP_AUTH_WECHAT_CLIENT_ID=
APP_AUTH_WECHAT_CLIENT_SECRET=
APP_AUTH_WECHAT_REDIRECT_URI=http://localhost:5173/oauth/callback/wechat

APP_AUTH_QQ_CLIENT_ID=
APP_AUTH_QQ_CLIENT_SECRET=
APP_AUTH_QQ_REDIRECT_URI=http://localhost:5173/oauth/callback/qq
```

上线时必须关闭 `APP_SMS_EXPOSE_CODE`，并把短信 provider 改为配置完整的阿里云实现。
